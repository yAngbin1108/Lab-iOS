# Lab

**iOS 内核工具箱 · IPA 分析 · 设备诊断**

基于 [lara](https://github.com/rooootdev/lara) 二次开发

iOS 16.0 – 18.7.1 · iOS 26.0.x

</div>

---

Lab 把两类工具合进了同一个 App：

- **内核工具箱** —— 通过 DarkSword 漏洞利用获得内核读写与沙盒外文件访问
- **分析工具** —— IPA 差异比对、本地化资源提取、包结构分析、崩溃日志归类
- **图标主题**（实验性，见下方⚠️）—— 移植自 lara/Cowabunga 的第三方图标主题

分析工具全部基于公开 API，**不依赖漏洞利用是否成功**。两者互不影响。

## 功能

### 🔧 内核工具箱

| 功能 | 说明 |
|---|---|
| **运行漏洞利用** | 执行 DarkSword，建立内核读写通道 |
| **获取内核缓存** | 抓取并解析内核缓存，得到符号偏移 |
| **初始化系统** | 完成后利用（VFS + 沙盒逃逸），开放全盘读写 |
| **重启桌面** | 软重启 SpringBoard |
| **触发 Panic** | 强制内核崩溃，设备立即重启 |

三种利用方式可在设置中切换：`VFS` / `SBX` / `Hybrid`（默认 Hybrid）。

### 📁 文件管理器

浏览沙盒之外的完整文件系统（`/System`、`/var`、`/private` 等），支持查看文件信息、读写、删除、递归搜索。

### 🧰 工具箱（分析模块）

五个模块都只使用公开接口，无需任何内核权限：

**IPA 差异分析**
对比两个 IPA 的文件增删改。两级比对：路径集合 → CRC32 → SHA-256 内容确认，输出可分享的文本报告。

**IPA 本地化管理**
提取 `.strings` / `.stringsdict`，支持 binary plist 与 UTF-8/UTF-16 两种格式，可导出 JSON / TXT 对照表。

**应用行为分析**
解析 Info.plist 全部键值、隐私用途声明、`embedded.mobileprovision` 里的授权信息、动态库清单与资源类型分布。

**运行监控**
导入 `.ips` / `.crash` 日志，识别异常类型与终止原因，按内存、断言、动态链接、权限等维度自动归类。

**系统能力检测**
设备与系统信息，以及内核读写通道的实时状态。

## 图标主题（实验性）

> ⚠️ **当前状态：功能未完成，在 iOS 17.5.1 上实测无法生效。**
> 代码已合并进本仓库并保留，但这是一个**已知失败的功能**。请先读完本节再用。

### 这个功能想做什么

给 iPhone 上的 App 换第三方图标主题（俗称"美化图标"）。实现路线移植自
[lara](https://github.com/rooootdev/lara) 的 DarkBoard（其本身源自
[Cowabunga](https://github.com/leminlimez/Cowabunga)），属于**文件替换派**：

1. 导入主题包（`.zip` / `.theme` / 文件夹，内含 `IconBundles/<bundle-id>.png`）
2. 枚举 `/Applications` 与 `/var/containers/Bundle/Application` 下的全部 App
3. 备份每个 App 的原始图标 PNG
4. 把主题图重绘成原图标的尺寸、压缩到不超过原文件的字节数
5. 借内核权限**直接覆写** App bundle 里的图标文件
6. 让系统重新读取图标 → 桌面显示主题样式

设计意图是"不注入 SpringBoard 进程"，从而避免运行时注入方案（如 SnowBoard）
带来的桌面崩溃风险。

### 实际做到了哪一步

前 5 步**完全正常**，有日志和校验为证：

| 环节 | 结果 |
|---|---|
| 主题导入 / 解压 / 按 bundle id 匹配 | ✅ 正常 |
| 备份原始图标 | ✅ 正常 |
| 写入 App bundle | ✅ **68 个 App 全部写入成功** |
| 读回磁盘校验 | ✅ 文件大小确实变了（`现≠原`），证明落盘无误 |
| **第 6 步：让系统重读图标** | ❌ **失败，图标不变** |

也就是说：**文件真的被改掉了，但你在桌面上看不到任何变化。**

### 为什么失败

iOS 17 的桌面图标不是每次重启都从 App bundle 现读的，而是走一层由
`iconservices` 维护的缓存。要让新图标出现，必须触发这层缓存重建。三条常规手段
在本机（iPhone15,4 / iOS 17.5.1 / Apple ID 自签）全部走不通：

**① `lsregister` 不存在**
标准做法是对每个改过的 App 跑 `lsregister -f <bundle>` 强制 LaunchServices 重索引。
但 iOS 17 已经移除了这个工具，代码探测了三个候选路径，均无。

**② `iconservices` 缓存目录无权限**
退而求其次，直接删掉缓存目录逼系统重建。但 `com.apple.IconsCache` 拒绝访问：

```
读不了 com.apple.IconsCache: The file "com.apple.IconsCache" couldn't ...
```

即使通过 `sbx_rootme()` 把本进程 ucred 的 uid 临时改成 0，依然被拒。

**③ 内核提权本身不可靠**
上面那句"uid 改成 0"其实是假象。日志里紧跟着的是：

```
(ds) setsockopt failed (early_kwrite32bytes)!
(ds) setsockopt failed (early_kwrite32bytes)!
(sbx) rootme: uid 501/501/501 -> 0/0/0     ← 报告成功
```

底层 `ds_kwrite32` 走的 socket 内核写通道**根本没写进去**，提权并未真正发生。
这个写原语在多次调用后会失效。

**④ 守护进程名也对不上**
尝试 `SIGKILL` 掉 `iconservicesagent` / `iconservicesd` 逼其重启，但 sysctl 全量
枚举进程后这两个名字都"未找到"。

### 结论

这不是"差一点就修好"，而是**这条路在 iOS 17.5.1 上缺少必要的系统支撑**：
既没有重索引入口，也拿不到缓存目录权限，而能绕过权限的内核写原语本身又不稳定。

上游 lara 作者把这个模块放在 `broken/` 目录并用 `.disabled(true)` 关闭，
Cowabunga 原作者也已停止维护相关分支——本次实测印证了这个判断。

### ⚠️ 使用后果（重要）

即便图标不会变，**点击「应用主题」仍然会真实改写 68 个 App 的图标文件**。
这会让这些 App 的代码签名校验不再成立，后果是：

> **之后从 App Store 更新任何一个被改过的 App，可能报签名错误而装不上。**

如果你已经点过，请务必执行还原流程：

1. 重新打开 Lab
2. 「内核」页依次完成 运行漏洞利用 → 初始化系统 → 初始化 SBX
3. 会自动弹出「图标还原」进度页，等它跑到"还原完成"

这一步会把备份的原始图标写回 bundle，恢复签名合法性。还原后不影响正常使用。

**如果不想冒险，就不要进入「图标」标签页点「应用主题」。** 其余所有功能
（内核工具箱、文件管理器、五个分析模块）与本节无关，不受影响。

### 如果你确实需要换图标

推荐零风险替代方案：用 iOS 自带「快捷指令」创建"打开某 App"的动作并指定自定义图标，
放到桌面。缺点是原 App 仍会留在桌面、启动时多一次确认，但不动系统文件、不掉签名。

## 安装说明

### 关于签名的一个常见误解

Lab 的内核功能**不依赖安装时注入的私有 entitlements**。

它的机制是：App 以普通方式签名安装 → 运行时通过 DarkSword 获得内核读写 → 再用 `sbx_escape` 从沙盒内部完成逃逸。也就是说，**系统是运行时被"说服"的，不是靠签名预先授权的**。

因此：

| 安装方式 | 能否工作 |
|---|---|
| Apple ID 自签（ESign / AltStore） | ✅ 正常 |
| TrollStore | ✅ 正常 |
| Xcode 真机调试 | ⚠️ 调试器附加时功能会被禁用 |

> 本项目早期文档曾要求必须使用 TrollStore，那是错误的判断，已更正。

### 支持范围

| 系统版本 | 状态 |
|---|---|
| iOS 17.0 – 18.7.1 | ✅ 支持 |
| iOS 26.0 – 26.0.1 | ✅ 支持 |
| iOS 16.x | ⚠️ 理论受影响，偏移未完整验证 |
| iOS 18.7.2+ / 26.1+ | ❌ 不支持 |
| A19 / M5 及更新芯片 | ❌ 因 MIE 无法使用 |

M 系列 CPU 设备如遇问题，可在 **设置 → 修改偏移** 中将 `t1sz_boot` 设为 `0x11`。

### ⚠️ 风险提示

- 漏洞利用存在失败概率，失败通常无害，重试即可
- **触发 Panic 会让设备立即重启**，正在写入的数据可能丢失
- 内核内存写入若越界，最坏情况需要恢复模式重刷系统
- 请先备份重要数据

本工具仅供在**你自己的设备**上研究与学习使用。

## 与上游 lara 的差异



### 新增的功能

- 图标主题模块（**实验性且当前无效**，详见[图标主题](#图标主题实验性)）
- 五个 IPA 分析与诊断模块

- 工具箱卡片式入口页
- 结构性 CI 自检体系
- 中文界面

### 修复的上游构建问题

| 问题 | 影响 |
|---|---|
| `CURRENT_PROJECT_VERSION = Release` | 非数字值，xcodebuild 直接报错 |
| 项目级 `IPHONEOS_DEPLOYMENT_TARGET = 26.0` | 未来版本号，构建失败 |
| 缺少共享 scheme | CI 里 `xcodebuild -scheme` 找不到目标 |
| 桥接头残留无实现的函数声明 | 编译能过但链接期失败 |

## 常见问题

**Q：点了「运行漏洞利用」没反应？**
A：检查是否有调试器附加（Xcode 运行时会出现此限制）。另外该功能本身有失败概率，重试是正常的。

**Q：文件管理器提示"未就绪"？**
A：需要先依次完成「运行漏洞利用」→「获取内核缓存」→「初始化系统」。

**Q：本地化管理显示"共 0 个本地化文件"？**
A：这是正常的。很多 App 把界面文字硬编码在代码里，不使用 `.strings` 文件。系统应用、社交类和游戏类应用的本地化文件通常较多。

**Q：能不能读取其他 App 的沙盒数据？**
A：完成「初始化系统」后可以。在此之前受沙盒限制。请注意这属于高权限操作，谨慎使用。

**Q：iOS 升级后还能用吗？**
A：不保证。漏洞利用与具体系统版本和内核布局强相关。
